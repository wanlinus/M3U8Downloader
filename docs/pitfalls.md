# 实现中踩过的坑

> 都是已经修掉的问题，留档以免重蹈覆辙。

1. **AES 填充策略**：HLS 的 AES-128 分片通常带 **PKCS7 填充**。若错误地用「无填充 + 截断到 16 字节整数倍」处理，每片会丢掉 4–15 字节，拼接后 **188 字节 TS 包整体错位** —— 文件大小看着正常、实测包同步率只有 2%，根本无法播放。本工具按 PKCS7 → 无填充+188 对齐 的顺序尝试并校验结果。

2. **密钥按长度分派**：部分源站把 AES-192/256 错标为 `AES-128`，所以要按**密钥实际字节长度**（16/24/32）决定算法强度，而不是照 METHOD 字符串走。

3. **IV 推导**：`EXT-X-KEY` 未显式给出 IV 时，按规范用**媒体序号**（`MEDIA-SEQUENCE + 索引`，16 字节大端）推导，而不是列表索引。

4. **重定向后 URL 作基准**：解析相对路径必须用 `HttpClient` 重定向后的**最终地址**，否则经 CDN 跳转会解析到错误域名。

5. **假 200 与截断响应**：不少源站用 `200 + HTML 错误页` 冒充成功，或提前截断响应。需要嗅探 HTML、校验 Content-Length。

6. **路径中的双斜杠不能归一化**：某些源的主清单是 `/20260906/xx//1395kb/hls/index.m3u8`，把 `//` 折叠成 `/` 会直接 404。

7. **WinUI 部署**：非打包（unpackaged）应用若不自包含，会因缺少 DDLM 包而弹「Windows App Runtime 组件缺失」。设 `WindowsAppSDKSelfContained=true` + `SelfContained=true` 可彻底免除依赖。

8. **勾选状态不会回写**：WinUI 的 `CheckBox` 双向绑定要求属性实现 `INotifyPropertyChanged`。Core 模型保持朴素，界面侧用 `EpisodeItemViewModel` 薄包装。

9. **并发是嵌套的**：站点模式下总连接数 ≈ 集数并发 × 每集分片并发（默认 2×16=32），不要盲目调大。

10. **别硬编码下载目录**：`%USERPROFILE%\Downloads` 与**系统真实下载目录**可能不是同一个位置（用户可以把「下载」文件夹移到别的盘）。而且 `%USERPROFILE%\Downloads` 往往**仍然存在**，于是程序会**静默存到错误的地方**——不报错，但你在下载文件夹里找不到文件。正确做法是向 Shell 查询 `FOLDERID_Downloads`（见 `Core/KnownFolders.cs`）。

11. **WinUI 下读命令行**：`Environment.GetCommandLineArgs()` 在 WinUI 的启动路径里不保证可靠（实测会返回空，导致启动参数失效），应改用 Win32 `GetCommandLineW`。

12. **PowerShell 脚本编码**：Windows PowerShell 5.1 读取**无 BOM 的 UTF-8** 脚本时会按系统 ANSI 代码页（中文系统为 GBK）解码。含中文的脚本若不加 BOM，中文字符的尾字节会把后面的引号吞掉 → 语法错误。含中文的 `.ps1` 请存为 **UTF-8 with BOM**，或只用 ASCII。
    - 补充：**程序在运行时生成 `.ps1` 也一样要带 BOM**（`new UTF8Encoding(encoderShouldEmitUTF8Identifier: true)`）。自动更新的收尾脚本就这么翻过车 —— 编译、启动都正常，只是脚本一跑就 `Unexpected token '}'`，排查半天才想起这条。

13. **根目录分片被整批当广告跳过**：目录聚类用「路径里最后一个 `/` 之前的部分」当目录键，而 `/seg0.ts` 的 `LastIndexOf('/')` 是 0，直接切片会得到 `/seg0.ts` 本身 —— 每个分片都成了独立目录，于是除第一片外全被标记为「异目录插播广告」并跳过。结果是一集只下了 1 片却报"成功"，产物小得离谱。目录键必须把这种情况归到 `/`。同时增加了保护：跳过比例超过 30% 时明确告警。

14. **绑定属性必须在 UI 线程改**：`SeriesTask` 的属性直接绑到 `ListView`，而下载回调来自后台线程。WinUI 里从后台线程改绑定属性**不报错但界面不刷新**，现象就是任务永远停在「下载中」，进度条一动不动。`DownloadTaskManager` 因此统一通过 `uiInvoker`（`DispatcherQueue.TryEnqueue`）封送所有状态写入；后台 worker 也不再去遍历绑定用的 `ObservableCollection`，改用内部待执行队列。

15. **暂存目录每次换名字 = 断点续传形同虚设**：暂存目录原本每次下载都新建一个带随机后缀的名字，于是上次下到一半的分片**虽然保留着，却永远不会再被用到** —— 关掉程序重开后整集重下。现在同一集已有暂存目录就直接复用，由引擎的清单指纹决定哪些分片还能用。

16. **异步封送下"先写后跑"的顺序**：恢复任务时要先把 `Series` / `Options` 写进任务对象再入队。`DispatcherQueue.TryEnqueue` 是**异步**的，如果写完就立刻入队，worker 可能先拿到任务、读到的却是 `null`，任务会直接判失败。这类"设置状态 → 交给后台消费"的地方必须等封送真正执行完（自检里就是靠这一点抓出来的）。

17. **「重试失败集」不该新建任务**：原先的实现是 `Enqueue(SelectOnly(task.Series, failedNumbers), …)`，也就是照抄剧集列表再建一个**新任务**。于是同一个任务在列表里出现两份：新任务把失败的 21 集从头再列一遍，老任务还挂着「已取消」，点一次「重试失败集」就多出一批重复的集。正确做法是**在原任务上就地重试** —— 失败的那几集回到「等待中」，已完成的集作为上一轮的成果带进报告但不重下。

18. **取消标记是一次性的**：`CancellationTokenSource` 取消过就废了。暂停/取消之后如果直接再入队，新的一轮会**一启动就被判取消**（界面上就是一句莫名的 "The operation was canceled."）。所以每次真正开始下载前都要换一个新的 `Cts`；「继续下载」里更要在**重新解析站点之前**就换 —— 那次解析用的就是这个 token。

19. **排队等并发名额的集会把整批下载拖垮**：暂停/取消时，还在 `SemaphoreSlim.WaitAsync(ct)` 上排队的那些集会让它抛 `OperationCanceledException`。这个异常冒到 `DownloadAsync` 外面，整批下载就以异常收场：任务被判成「失败」，连下载报告都拿不到。必须在入口处接住它，按「还没开始下载」处理（暂存目录里的分片照旧保留）。注意这段 catch **不能**并进下面那个带 `finally { gate.Release(); }` 的 try —— 名额根本没拿到，Release 会把信号量计数搞坏。

20. **暂停不是取消**：暂停后如果只把状态对成 `Canceled`，用户看到的是「已取消」，还会同时冒出「继续下载」和「重试失败集」两个语义矛盾的按钮。暂停要有独立状态（`Paused`），并且只把**被暂停打断的**那些集改写成「已暂停」——暂停那一刻**真的**失败的分集（比如源站刚好 404）要如实保留，否则等于把真实问题藏起来。

21. **进度上报必须限流，但收尾那一次不能省**：引擎每几十毫秒上报一次，每次都 `DispatcherQueue.TryEnqueue` 一个闭包的话，UI 线程会被写入淹掉，表现就是"进度条不动、消息一句话不变"。限流到 100ms 一次之后就顺了。**但轮次收尾那次必须强制放行**——它带着各集的最终状态，被限流吃掉的话分集行会永远停在「下载中」（自检阶段 D 抓到的就是这个）。

22. **"百分比不动"不等于"没在下载"**：一集可能有近千个分片，百分比在几十秒里看起来是同一个数。界面必须显示分片计数（`183/941 片`），并且让每一轮明确写出"这一轮领到了哪几集"——否则用户没法判断程序在下什么。

23. **多源站点按集号选集会重复下载**：`SiteSeries.AllEpisodes` 是"所有源 × 所有集"的笛卡尔积，同一个集号在不同源上都有一份。用 `SelectOnly(series, {12})` 这种"只按集号"的写法，会**一次选中好几个同号集**，引擎于是把第 12 集下了两遍（诊断日志里是 `计划 2 集（12,12）`）。选集必须按 **(源 id, 集号)** 成对匹配。

24. **`UseProxy` 默认为 `true`，「直连」客户端会被偷偷套上系统代理**：`SocketsHttpHandler` / `HttpClientHandler` 的 `UseProxy` 默认是 `true`，而 `Proxy` 为 `null` 时它会退到 `HttpClient.DefaultProxy` —— Windows 上读的就是系统 WinINET 设置。用户机器上开着 Clash 之类的工具时，`SiteContext.Direct` 和 `HlsDownloader` 里那份"直连"客户端会**全程走代理**：页面解析被按代理 IP 拒绝（实测影迷界影院：真直连 200 / 走系统代理 403），分片下载则白吃掉用户的代理流量 —— 而"国内站零代理开销"恰恰是这套设计存在的意义。凡是要直连的 handler 都必须**显式**写 `UseProxy = false`；自检阶段 K 把进程默认代理指到一个黑洞来守住这条。

25. **「连接超时」不等于「站点不可达」**：连接超时压到 5 秒是为了让被墙站点早点回退代理，但慢站点（挂在 Cloudflare 后面的）直连耗时会在 0.9s~30s 之间剧烈波动。把"慢"当成"不通"，就会走进「回退代理 → 代理 IP 又被站点 403」的失败链，本来能成功的请求被判死。所以回退链上得留一手：代理那条路也失败时，用一个连接超时放宽到 30 秒的直连客户端再试一次。

26. **苹果 CMS 不止一种 URL 形态，详情页 ID 也未必等于播放页 ID**：`MacCmsAdapter` 起初只认 `/vodplay/{id}-{sid}-{nid}.html`（伪静态）。实测至少还有两种：原生形态 `/index.php/vod/play/id/{id}/sid/{sid}/nid/{nid}.html`（欧乐影院），以及斜杠形态 `/play/{id}/{sid}/{nid}.html`（影迷界影院）。更麻烦的是**斜杠形态的站点常常有两套编号** —— 详情页 `/t/62329.html` 是 62329，播放页却是 `/play/2337178967/…`。原先"按详情页 ID 过滤剧集链接"的写法会把本剧链接全部滤掉，最后误报"页面里既没有 player_aaaa 也没有剧集链接"。正确做法是**先收集、再投票**：优先取与详情页 ID 相同的那个，取不到就取页内出现次数最多的那个（要求至少 2 次，免得把日期型误匹配当成剧集）。

27. **CI 发 Release 用 `softprops/action-gh-release` 传大包会超时**：它底层 HTTP 客户端等响应头有 300 秒上限，上传 87 MB 主包时 GitHub 端没回响应头就直接报 `Headers Timeout Error`，整个 Release 步骤失败且什么都不留。v1.4.2 首发就是这么挂的（构建、自检全绿，只挂在最后一步）。改用 runner 预装的 **`gh` CLI**（Go 客户端，无此限制），并写成幂等：release 已存在就 `upload --clobber` + `edit`，不存在才 `create` —— 重跑 CI 也不会撞出"release 已存在"的错误。

28. **分集行的「已完成」可能只是字面**：一轮下载的收尾回填原来只写 `StatusText`，`State` 和 `OutputPath` 指望引擎最后一次进度快照补上。但快照走 `Progress<T>` **异步**到达，经常落在收尾闸门（`roundFinished`）之后被整批拦掉 —— 于是行上写着「已完成」，`State` 还停在 Downloading、`OutputPath` 是空。后果是「继续下载」把这集当成没下过的再下一遍（续下自检阶段 N 首跑就抓到了）。**收尾回填必须把 `State` 与 `OutputPath` 一起写死**，快照只能锦上添花，不能是唯一来源。

29. **`Microsoft.Data.Sqlite` 默认开连接池，库文件被程序一直占着**：连接 `Dispose()` 之后底层句柄仍然留在池里，于是 `downloads.db` 被锁住 —— 用户想删掉它、备份一份、或拿 DB 工具打开看一眼，都会撞上 `The process cannot access the file ... because it is being used by another process`。这个坑是在单独验证 SQLite 实现时读文件头发现的（`File.OpenRead` 直接抛 IOException）。我们的写入频率极低（一轮下载几十次），池化省不下什么，所以在连接串里显式写 **`Pooling = false`**，用完即关。顺带：`busy_timeout` 要设（并发写时等一下比直接失败好），所有读写都要吞异常 —— 历史记不上绝不该影响下载。**没引 `SqliteDatabase` 的地方也要记住这条**：任何"造一个库文件出来给别人用"的代码（自检里的临时库、`_diag` 诊断、手工建库的脚本）都必须自己带上 `Pooling=False`，默认连接串会把文件锁到进程结束。**排查手法**：怀疑某个文件被占着时，用 `FileShare.None` 试开一次就能坐实；如果怀疑是自己代码占的，把那段换成不吞异常的版本跑一遍，异常会直接指出 `IOException: ... being used by another process`（当年文件迁移那段代码就是这么查出来的 —— 迁移逻辑后来删了，但这个手法留着）。

30. **「下过没有」要以磁盘文件为准，不能只信记录**：任务列表会被「清理已完成」清掉、重装程序或换台机器就没了，但视频还好好躺在文件夹里。补更（续下）时如果只查记录，用户会看到一堆"没下过"的集，勾了就是重复下载几百 MB。正确做法是拿文件名模板**正向**算出每一集该叫什么名字，再看目录里有没有这个文件（详见 `EpisodeFileScanner`）—— 正向算才能和下载时用的是同一套规则（`{title}` 会过一遍非法字符替换、集号有补零差异，用正则反向猜模板必然出错）。记录与下载历史降级为辅助：只用来解释"为什么没有"（上次失败 / 曾下载过但文件已不在）。注意空文件不算下过（中断会留下 0 字节文件）。

31. **刷新元数据时别把旧的请求头冲掉**：站点快照里的 Referer / Origin 是分片与清单请求必须带的（`SeriesDownloader` 里 `headers = new(series.Headers)`），而"重新解析页面刷新快照"这条路径拿到的新 Headers **可能是空的** —— 通用兜底解析器就不填 Referer。直接覆盖等于把原来存好的头抹掉：快照里集号、标题都还在，看起来一切正常，只是下次用快照续下时**每个分片请求都被站点 403**。正确做法是**旧头铺底、新头覆盖**。自检阶段 P 用"重启恢复后快照里还剩几个请求头"守住了这条。

32. **`IsFinished` 里包含「暂停」和「取消」，别拿它当"下载完成"**：`SeriesTask.IsFinished` 的语义是"任务已经停下、可以继续/重试/移除"，所以 `Paused`、`Canceled` 都算在内。拿它当完成类提示的判据，用户**一点暂停就会弹「已自动过滤 N 个广告」**（实机反馈的 bug）—— 暂停是他自己按的，弹这个窗像是程序在催他什么。要判"这一轮真的跑完了"用 `IsRoundFinished`（完成 / 部分完成 / 失败）。项目里其它几处 `IsFinished` 的用法（能不能继续、能不能重试、清理已完成）语义都是对的 —— 新增判断前先想清楚自己要的是哪一个。

33. **移除任务要连同它的下载历史一起销掉，但别在 UI 线程上删**：任务被移除后，它那本"下过的账"只剩误导 —— 下次再下这部剧，预检会凭记录说出"曾下载过（N MB），文件已不在"，而那个文件是用户连同任务一起清掉的。所以 `Remove` 里要调 `IDownloadHistoryStore.Forget(pageUrl)`，**按整部剧销**而不是只销任务里现有的那几集（续下时可以只勾一部分，历史里还躺着更早下过、任务记录已经忘掉的集）。两个注意点：① 删除是磁盘 I/O，而 `Remove` 是按钮直接调的，不能压在 UI 线程，扔 `Task.Run`；② 与 worker 收尾的 `RecordHistory` 存在竞态 —— 移除一个**正在下载**的任务时，`Cancel` 之后 worker 收尾仍会把这一轮已下好的集写回去，库里留下几行。这几行本身是真的（文件确实下出来了），也不影响"磁盘优先"的判定，不值得为它加锁。**「清理已完成」不走这条**：那只是收拾列表，视频还在盘上，账留着才能在文件被删掉时说出"这集下过"。

34. **`EnableMsixTooling` 删不得：它同时是资源索引进 `publish` 的条件，删了发布包缺 PRI、启动即崩**：这个属性名字像"打包成 `.msix` 的开关"，本仓库又是非打包应用（`WindowsPackageType=None`），看起来完全不需要它。但 `Microsoft.WinUI.targets` 把它的默认值定成 `false`，而 `Microsoft.WinUI.AppX.targets` 里要 `OutputType==WinExe && EnableMsixTooling==true` 才处理资源索引 —— **删掉之后 `dotnet build` 照常生成 bin 下的 `M3U8Downloader.pri`，可 `dotnet publish` 不会把它复制到发布目录**。发布包少了 PRI 就是少了 XAML 资源索引，双击报 `XamlParseException`（0x802B000A）、窗口都出不来，而 build 与 publish 的输出里**一个警告都没有**。验证办法：`dotnet publish -o <一个空目录>`，然后看 `M3U8Downloader.pri`（约 2.2 MB）在不在。
    **这个坑是"把推断当结论"踩出来的**：当时看到 `Microsoft.Windows.SDK.BuildTools.MSIX` 里挂着 `RemoteDeploymentType` / `vs.appxrecipe` 那套部署目标，就推断"IDE 索要开发者模式是它引起的"；删掉之后 IDE 确实不报了 —— 但那多半只是**巧合**（重载项目也会消掉那个提示），而删它的确定后果直到跑完整发布才暴露。两条教训：① **改构建属性之后必须跑一次真实发布、并把产物启动起来**，"编译成功 / 发布成功"证明不了任何事；② IDE 索要开发者模式是 IDE 那边的事（换 run configuration 类型，或者按系统提示开启开发者模式），**不要拿项目属性去凑**。

35. **Windows PowerShell 5.1 按 ANSI 读无 BOM 脚本 —— 仓库里的 `.ps1` 必须 ASCII-only**：`scripts/` 下的脚本都没有 BOM，而 PS 5.1 对无 BOM 文件用的是系统 ANSI 代码页（这台机器是 GBK）。UTF-8 的中文是 3 字节，按 GBK 双字节读就会**落单一个字节**，它与后面的字节重新组合，最典型的后果是**把字符串的结束引号吃掉**：`Write-Host "核心库构建失败"` 是 7 个汉字 = 21 字节（奇数），整行解析成 `"内核库构建失败? -ForegroundColor Red; exit 1` 这种残缺字符串，脚本报 `The string is missing the terminator` **整个跑不起来**。`build.ps1` 就这么坏了很久没人发现（它不在 AGENTS.md 的常用命令里，也没人跑过它）。更阴的是**侥幸成立**的情况：`publish.ps1` 里也有一行中文注释却一直正常 —— 因为它在注释里、且位于行尾，落单字节吃掉的只是 `\r`，语法不受影响。所以别用"它现在能跑"当证据：规则是 **`scripts/` 下的 .ps1 一律 ASCII-only**（两个脚本头部都写了这条注释）。CI 里没事是因为 `shell: pwsh` 是 PowerShell 7（默认按 UTF-8 读脚本），**只有本地 PS 5.1 会中招**。自查手法：`[System.IO.File]::ReadAllBytes()` 数一遍 `> 127` 的字节，再用 ANSI 解码后交给 `Parser::ParseInput` 跑一遍。注意这条和"提交信息文件要用**无 BOM** 的 UTF-8"**方向相反** —— 那个文件是给 git 读的（BOM 会混进提交标题），脚本是给 PS 5.1 读的（中文要么带 BOM，要么干脆别写）。

36. **`MediaPlayerElement` 自己建的 `MediaPlayer`：不要 Dispose（会崩），但也不能不管（关了还在放）**：`MediaPlayerElement.MediaPlayer` 是**按需自动创建**的（第一次访问那个属性时它就建一个）。这种"它建的"播放器由它自己收拾 —— 外部调 `Dispose()` 就出事：在窗口关闭途中释放它，**`Window.Close()` 本身**会抛 `COMException 0x80004004`（E_ABORT），异常在事件处理器里没人接，于是整个进程崩掉。实机表现是"关掉内置播放器，整个软件跟着消失"，很容易误判成"退出时机不对"（我一开始就往 `DispatcherShutdownMode` 上找）。**但把 Dispose 删掉就完事了吗？不行** —— 元素什么时候回收它那个播放器是它的事，窗口关掉之后声音会留在后台继续放（第二个实机反馈）。正确的分寸是**"停 + 松开媒体"，不是"释放"**：`player.Pause()` 加 `player.Source = null`，在 `AppWindow.Closing`（关窗前）与 `Closed`（关窗后兜一次）各调一次，播放器引用缓存在字段里、`Closed` 时不必再回头访问 XAML。
    **排查手法**（两次都靠它定位）：加一个临时入口把用户那套操作自动走一遍、每步打一条日志，并**把播放状态也读出来**。第一次的日志停在"播放窗口已打开"、进程退出码 `0xC000027B`、崩溃日志里 `Window.Close()` 的堆栈把问题钉死；第二次光看"窗口没了"是看不出后台在放的，读到 `Playing → None` 才算证明确实停了 —— 修复后两次都是退出码 0、无崩溃日志。

37. **解析规则没认出来，往往是"过滤器"先动的手 —— 别一上来就怀疑正则**：影迷界影院（wakuredo.com）的搜索结果，严格解析报 **0 条**、宽松解析给 28 条全是页脚推荐位，看起来像"结果条目的结构化特征没匹配上"，于是我反复去调 `ExtractTitle` 里 `alt` / `<div class="nm">` 那两条正则。**实际原因在它们更前面**：`LooksLikeDetailPage` 是白名单（`voddetail` / `/t/` / `/vod/` / `/detail/` …），而**这个站的搜索结果条目是 `/video/{id}.html`** —— 真实命中在"像不像详情页"这一步就被整条丢掉了，压根走不到取标题。补上 `/video/` 之后，同一份页面直接出 18 条真结果（`交锋` 排第一）。
    两条教训：① **先分段验证**（把"链接形态过滤"和"标题提取"各自的结果打出来），别直接盯着最后一步的输出猜；② **白名单式过滤一定要配一个反例自检** —— 现在自检阶段 R 里同时钉住了"`/video/` 要认"和"斜杠形态的 `/play/{id}/{sid}/{nid}.html` 不能认"（同一个`/video/` 前缀后面也可能挂播放页）。顺带：`SearchSite.TryResolve` 拦不住"域名打错"，因为 `.NET` 的 `Uri` 接受**中文域名**（IDN）—— `https://不是地址` 是合法地址，别拿它当"非法输入"的反例（我第一版自检就是这么写错的，被自检自己抓出来了）。
    另外 `<img alt="…">` 也可能挂在角标图上（`alt="更新至04集"`），所以那个 `alt` 取出来之后同样要过一遍 `LooksLikeStatusText`，否则剧名会变成"更新至04集"。

38. **要自动验证 WinUI 界面，用 UI Automation 驱动 + 截图，别用物理鼠标和 SendKeys**：为了确认新界面真的渲染出来（而不是只"编译通过"），写了个 `_diag` 脚本驱动界面截图。第一版用 `SetCursorPos` + `mouse_event` 点按钮、`SendKeys` 输中文，结果截图拍到了**浏览器** —— `SetForegroundWindow` 在调用方不持有前台时会被系统拒绝，而物理点击落在屏幕坐标上，谁在前台就点谁。可靠的做法是三条：① **交互全走 UIA 模式**（`Button` 用 `InvokePattern`、`ToggleButton` 只支持 `TogglePattern`、`TextBox` 用 `ValuePattern.SetValue`，物理点击一概不用）——顺便发现 `FindByName` 对 TextBox 拿到的是 **Placeholder 文本**，输入后也不变，所以别用它判断框里有没有内容；② **真要抓屏就先把窗口抢到前台**：`AttachThreadInput(自己线程, 前台线程, true)` → `ShowWindow` → `BringWindowToTop` → `SetForegroundWindow`，再 `CopyFromScreen`（`PrintWindow` 对 WinUI 的 DirectComposition 内容经常拍出黑图）；③ 截图之外**把 UIA 控件树也打出来**（控件类型 + 名字），它才是"绑定到底生没生效"的硬证据 —— 光看图分不清"没渲染"和"渲染了但没数据"。
    还有一条环境坑：**应用是单实例的（`Local\M3U8Downloader.SingleInstance`）**，用户从 IDE 里跑着一个实例时，新进程会走"已有实例"分支**静默 exit 0** —— 脚本会看到"进程早早退出、退出码 0、没有窗口"，很容易误判成崩溃。脚本里先 `Stop-Process` 掉残留实例，那之前先问过用户（正在下载的任务会被打断）。

39. **类名匹配不能图省事写 `\b`：`-` 和 `_` 在正则里算单词字符**：抓结果条目时想取 `<a class="TagBookList_intro">` 里的简介，写的是 `class\s*=\s*["'][^"']*\bintro\b[^"']*["']`，结果**一条都匹配不上** —— `TagBookList_intro` 里 `intro` 前面是 `_`，两边都是单词字符，`\b` 根本不成立。同一个坑还有个反向版本：`[^"']*ep[^"']*` 这种纯子串匹配会把 `class="episode"` 也吃进来。正确写法是把类名当**整词**匹配：两侧必须是分隔符（空格 / `-` / `_`）或属性引号的边界，于是 `ep` 能匹配 `class="ep"` 与 `class="pic ep"`，但匹配不到 `class="episode"`（见 `SiteSearch.ClassAttr`）。
    顺带一个同源的小坑：**`Clean()` 里要先解 HTML 实体、再压空白**。`&nbsp;` 解出来是不换行空格（U+00A0），顺序反了的话它落在"压空白 + Trim"之后，就从 trim 底下溜过去 —— 类型会显示成「国产␣」这种带尾巴的样子。

40. **`ListViewItem` 默认按内容宽度收缩，卡片里的 `*` 列会整列塌掉**：搜索弹窗里照网站排的卡片是「海报（固定宽）+ 剧名/简介（`*`）+ 角标（自动）」，XAML 写得没问题、`ListView` 也占满了弹窗，但渲染出来简介被挤成八行、整张卡片缩在左边一小条。原因是 `ListViewItem` 的默认 `HorizontalContentAlignment` 不是 `Stretch`，条目按内容量收缩，`*` 列没了可分的空间。修法是在 `ListView.ItemContainerStyle` 里给 `ListViewItem` 设 `HorizontalContentAlignment="Stretch"`。**这个坑只在"条目内部有 `*` 列 / 需要撑满"时出现**，纯左对齐的列表（比如续下更新的勾选列表）看不出来，所以很容易在写新卡片时再踩一次。

41. **UI Automation 查不出"到底是谁触发的"时，让程序自己说**：验证搜索弹窗时，控件树显示"搜索按钮压根没被点到"（`FindByName` 命中的是按钮里的 `TextBlock`，不是按钮本身），可结果却出来了、还自动选了一部剧，一路推了两个小时。最后在 App 里加了个临时的 `SearchTrace`（把 `OnOpenSearch` / `OnSearch` / `SearchAsync` 的站点与关键词 / `OnHitClick` / `UseSearchHit` 各写一行到程序目录下的日志），一跑就真相大白：**链路本来是对的**，之前那次的怪现象是上一轮残留的实例没杀干净、UIA 驱动的其实是那个旧进程。三个教训：① 外部观测推不出来时，加**临时**日志（查完就删，别留进仓库）；② 顺带发现 `Button` 的 `Content` 是 `StackPanel` 时 **UIA Name 是空的**（不会去取里面 `TextBlock` 的文字）—— 给按钮加 `AutomationProperties.Name` 既是无障碍该做的事，也让自动化脚本能稳定点到它；③ 脚本每次跑之前先把残留进程杀干净，否则观测到的根本不是你以为的那个实例。

42. **站点卡片上那句"更新至N集"不能信，它是 MacCMS 的 `vod_remarks`（手填、会过期）**：搜索弹窗一开始把结果页的角标原样搬到卡片上，用户一眼看出不对 —— 青苹果影院给《交锋》写的是 **「更新至04集」**，而点进去列出 **第 01 集…第 28 集**。
    **先排除"我们取错了"**：把每条 `totalChapterNum` 连同上下文打出来，发现它紧跟在自己那张卡的海报后面、`href` 也和卡片一致，配对没问题；再用**我们自己的 UA / Chrome UA / curl 默认 UA / 经用户代理**四种方式抓同一页，拿到的是**逐字节相同**的 HTML（连长度 22229 都一样），页面上人眼看到的文字也确实是「更新至04集」。**是站点自己的搜索索引和详情页对不上**，不是解析错位。
    **结论**：这个字段不能当集数用，解析时直接丢掉（`SiteSearch.IsUpdatingBadge` 判 `更新…` 前缀），只留 `全9集` / `已完结` / `HD中字` 这种**结论性**标记 —— 它们说的是"就这样了"、不随时间漂移，正好用来分辨"是电影还是连续剧、完结没有"。自检阶段 R 一正一反各钉一条（「更新至04集」必须丢、「全9集」必须留）。
    **方法上的教训**：怀疑"取值取错了"时，**先把原始 HTML 里这个值的前后文打出来、再做多 UA/多链路的同一请求去比对**。这两步能干脆地区分"我们解析错位"和"数据源本身就是错的"，比盯着最终渲染结果猜快得多。顺带：那个"页面长度四种抓法完全一致"本身就是很有力的证据 —— 说明不是 CDN 按 UA 或按出口 IP 发了不同版本。

43. **发布流程只由 tag 触发，于是"两个 tag 之间的提交从来没上过 CI"**：v1.5.0 打 tag 后发布流程挂在「自检」这一步，而本地把能想到的跑法全试了一遍都通过 —— Debug / Release / 全新克隆 / 清空 `bin`+`obj` / 用 `DOTNET_PROCESSOR_COUNT=2` 限核 / 把 ffmpeg 藏起来（阶段 G 在 CI 上没有 ffmpeg）。**排查卡住的原因不是失败本身，是看不到 CI 的输出**：Actions 的作业日志与 artifact 都要仓库管理员权限（`GET .../actions/jobs/{id}/logs` 直接回 `Must have admin rights to Repository.`，artifact 下载 401），而 job 页面的 HTML 里只有外壳（日志是前端拉的）。
    **拿到输出的办法**（不动 master）：开一个临时分支，只放一个诊断 workflow，让它把自检输出 `Tee-Object` 到文件、再 `git push -f` 到一个 `diag-log` 分支 —— `raw.githubusercontent.com` 是**匿名可读**的（记得加 `?t=<ticks>` 破缓存）。一跑就真相大白：**同一份代码在 CI 上是 `自检结果: ✔ 通过 / EXITCODE=0`**。
    **真正的教训有三条**：
    ① **那次是偶发**，重推一次 tag 就过了。所以排查 CI-only 失败，**第一步应该是"同一份代码重跑一次还挂不挂"**，而不是先去追环境差异 —— 否则会花几个小时找一个不存在的 bug。
    ② **盲区是真的**：发布 workflow 只有 `on: push: tags: ['v*']`，所以 v1.4.2 到 v1.5.0 之间的 **12 个提交（统一库、内置播放器、站内搜索）一次都没被 CI 跑过**，直到打 tag 那一刻才第一次上 CI —— 而那时"挂了"的代价最大（tag 已推、Release 没出）。**自检应该挂在 master 的 push/PR 上，tag 只负责打包发布。**
    ③ 临时诊断用的 workflow 和分支，**用完立刻删**（`git push origin --delete`），别让它留在仓库里。
    顺带一条仓库现状：`windows-latest` 是 **4 核**（不是 2 核），OS `10.0.26100`，`[System.Text.Encoding]::Default` 是 `utf-8` —— 别再按"2 核慢机器"去推断。
