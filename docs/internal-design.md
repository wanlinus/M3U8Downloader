### 分层与依赖方向

```
M3U8Downloader.Core        ← 引擎、编排、持久化都在这里（唯一第三方包：Microsoft.Data.Sqlite）
      ▲              ▲
      │              │
    App          SelfTest
```

- **只允许单向依赖**：App / SelfTest 都只引用 Core，Core 从不反向引用它们
  （`Core.csproj` 里没有任何 `ProjectReference`；`PackageReference` 只有 SQLite 一个，
  理由与那笔账见 `AGENTS.md` 的「存储」一节）；
- Core 内部按职责分层：引擎（`HlsDownloader`）→ 单集流水线（`Downloads/EpisodePipeline`）→
  站点协调（`Sites/SeriesDownloader`）→ 任务队列（`Tasks/DownloadTaskManager`）；
- 界面只做两件事：把参数递进去、把日志与进度搬上来 —— **下载流程不写在 ViewModel 里**。

### 一条流水线，两种模式

「单文件下载」和「站点批量下载」曾经是两套并行实现：单文件那份写在
`MainViewModel.StartAsync()` 里，自己 new 引擎、自己跑解析与下载；于是站点模式有的
转 MP4、时长核对、产物体检、暂存目录指纹，它一样都没有。

现在两者都归结到 `Downloads/EpisodePipeline.RunAsync()`：

| 类型 | 负责 |
|---|---|
| `EpisodePipeline` | 一集的完整流程：解析清单 → 下载到暂存目录 → 转封装 MP4 → 容器探测 + 全量解码检查 → 清理暂存 |
| `SingleFileDownloadService` | 单文件模式入口：一个地址 → 一个产物 + 一份 `xxx-下载报告.md` |
| `SeriesDownloader` | 站点模式协调器：集间并发、进度聚合、分集报告与续传 |

流水线本身**不含任何站点概念**（没有剧集、没有集号），输入就是「一个播放列表地址 +
一个暂存目录 + 一个输出文件名」—— 所以图形界面里的单文件模式与站点模式走的是同一段代码，
校验强度不会再出现落差（自检的阶段 I 守着这条）。

### 站内搜索

搜到的东西直接喂给上面那条既有链路，"搜索"本身不碰下载：

```
站点下拉框（sites 表）
   ↓ 选中的站点根地址 + 关键词
SiteSearch.SearchAsync()
   ├─ 抓站点**首页** → 读 <form> 拿到 action 与关键词字段名   ← 搜索路径不靠猜
   ├─ 按表单拼出搜索地址 → 抓搜索页
   └─ ParseHits()：先严格（只认结果条目特征）→ 一条都没有才宽松
   ↓ 命中列表（剧名 + 详情页地址 + 海报/角标/类型/简介）
SearchDialog 的海报卡片列表（海报走 SiteContext.GetBytesAsync，同一条代理回退链）
   ↓ 点一部
地址填进「播放页地址」→ 与手工粘贴走同一条解析路线
```

四条设计约束（都是实测撞出来的，详见 `docs/pitfalls.md` 第 37 / 39 / 40 条）：

- **搜索入口读首页表单，不写死路径**。苹果 CMS 各家的搜索路径毫无规律，
  首页 `<form>` 里的 `action` + 字段名是唯一可靠来源 —— 换模板、换域名都不用改代码；
- **严格优先、宽松兜底**。严格模式只认"结果条目"才有的特征（海报 `alt` / `<div class="nm">` /
  章节数角标），否则页脚推荐位的纯文本链接会混进来（实测一次能混 28 条）；
- **认不出详情页形态的站会被整站滤空**。白名单里少了 `/video/` 这种形态，
  表现就是"严格解析 0 条" —— 所以自检阶段 R 同时钉住了该认的与不该认的（斜杠播放页）；
- **结果给足信息**。同名剧太多（搜「交锋」出来六部不同的），卡片必须带海报、类型和简介，
  才认得出要的是哪一部 —— 这也是它做成弹窗而不是主界面一行列表的原因。
- **站点给的角标不能照单全收**。`更新至N集` 是 MacCMS 的 `vod_remarks`（上传者手填、
  经常不更新），实测同一部剧搜索页写"更新至04集"、详情页却有 28 集，所以解析时就丢掉；
  只留 `全9集` / `已完结` / `HD中字` 这类结论性标记。

站点清单落在统一库的 `sites` 表里，由用户在「站点管理…」里维护：这类站换域名很勤，
写死在代码里的清单过一阵就是一堆死链。

## 产物校验（下载完到底查了什么）

下载完成时，"成功"不是靠一句 `OK` 得出的，而是逐层查出来的。**没通过校验的一律不算成功**：

| 层级 | 查什么 | 不过会怎样 |
| --- | --- | --- |
| 清单/密钥 | 响应不是 HTML/JSON 错误页（挡"假 200"） | 报错并停止，不做无意义的重试 |
| 每个分片 | HTTP 2xx + `Content-Length` 与实际字节数一致（挡截断响应） | 该片重试，仍失败即计失败 |
| 解密结果 | TS 同步字节 `0x47`（严格版查 20 个包起点，宽松版用来在多种填充策略里挑正确解） | 换备用密钥再试，仍不行才算失败 |
| 分片落盘 | 应该存在的分片**是否真在磁盘上**、大小是否与记录相符 | 记为"落盘核对异常"并写进报告 |
| 合并结果 | 字节数与"应拼入的分片之和"完全相等（不多不少） | 判为不完整，**不清理暂存目录** |
| TS 产物 | **全量逐包** 188 字节对齐（400MB 约 1 秒） | 判为"拼接错位"，保留现场 |
| 产物时长 | 用内置探测（TS 读 PCR / MP4 读 mvhd）读真实时长，与清单声明值比对（容差 5% 且 3s） | 报"可能缺片"，建议核对原播放列表 |
| **产物解码** | `ffmpeg -f null -` 整条解一遍，统计坏包/时间戳告警 | 报告里标"有解码告警"，并列出是哪几集、报了什么 |

"合并字节数核对"和"产物时长核对"是后补的两道闸门 —— 它们堵的正是那种最阴的失败：
**分片少了、产物静默缺一段，但 ffmpeg 退出码是 0、文件大小看着也正常**。

时长核对优先用**内置探测**，不依赖外部工具：TS 累加 PCR 相邻差值（天然容忍计数回绕），
MP4 读 `moov → mvhd` 的 duration/timescale。两边都读不出来时会明确报"时长核对未完成"，
**不会**假装通过。

### 仍然查不到的（如实说明）

- **解码正确性**：只查 TS 包同步字节，不查 H.264/AAC 内容是否有损坏。源站本身返回坏数据时，
  产物能通过格式校验，但播放器可能出现花屏/丢帧（实测 16 集里有 3 集报 `Packet corrupt`，
  是源站数据问题，不是拼接问题）。
- **音视频是否同步**：不做 A/V 同步检查。
- **时长核对依赖流里有时间戳**：既没有 PCR 时间戳、也没有 ffmpeg 的极端情况下读不出时长，
  只能报"未完成"。

自检阶段 G 会验证"内置时长探测"本身：构造一条 PCR 跨度为 42 秒的 TS，要求读回 42.00s。

## 暂存目录与校验（一集一个目录，全过才清理）

每一集下载时都使用**自己专属的暂存目录**，就放在**下载目录里面**：

```
下载目录\交锋\
├── 交锋.01.mp4                     # 最终产物（常用格式）
├── 交锋-下载报告.md
└── .m3u8tmp-001-a1b2c3d4\          # 本集的暂存目录（成功后自动删除）
    ├── manifest.json               # 清单：播放列表、分片数、时长、跳过项、指纹、产物路径
    ├── seg_000000.ts               # 分片
    └── merged.ts                   # 合并后的中间文件
```

- **放在下载目录里**（而不是系统临时目录）：便于发现与清理，出问题时也容易找到；
- **名字带集号与随机串**（`.m3u8tmp-<集号>-<8位随机>`）：同一集并发/重试时不会互相踩；
- 流程：**下载 → 合并 → 转 MP4 → 全量校验 → 全部通过才删除暂存目录**；
- **中间任何一步出错都不删**：失败时暂存目录连同分片一并保留，
  报告里会写明路径，便于排查或下次重试；
- **再次下载同一集时直接复用这个目录**：里面已经下好的分片跳过不重下，剩下的接着下。
  复用是安全的 —— 分片还能不能用由下面说的清单指纹判断。

### 为什么清单里要存"指纹"

源站可能**每次请求都重新生成播放列表**（典型做法是随机插播广告），于是
「分片序号 ↔ 内容」的对应关系在不同次请求之间会变。若直接复用上一次的残留分片，
就会拼出一个**错位的文件** —— 而且大小往往看着很正常，极难发现。

因此续传前先比对指纹：

| 情况 | 处理 |
|---|---|
| 指纹一致 | 复用已有分片，正常断点续传 |
| 指纹不一致（列表被重新生成） | **丢弃旧分片重新下载**，并在日志里说明原因 |
| 有分片但没有清单（旧版本残留） | 同样丢弃 —— 无法确认对应关系 |
| 目录里有非本程序生成的文件 | 只清理自己的分片，**保留目录**，绝不误删用户文件 |

### 校验强度

合并产物做的是**全量逐包检查**：每个 188 字节包的同步字节都必须是 `0x47`，
且文件长度必须是 188 的整数倍。

早期实现只在"文件头、正中间、尾部"各抽查 3 个字节 —— 中间任何位置错位都发现不了，
那种校验基本没有意义。全量扫描 400MB 约 1 秒，代价完全可以接受。

## 续下更新：怎么判断"这集下过没有"

热播剧每天补更几集，用户既不想重建任务，也不想把已有的集重下一遍。点任务卡片上的
「续下更新」后是**两段式**：

1. **快照秒开**（`PreviewFromSnapshotAsync`，**不联网**）：首轮入队时就把"站点上全部集"
   的元数据存进了 `SeriesTask.Snapshot`（集号、标题、播放页地址、站点集标识、播放源、
   以及**请求头**），所以点一下就能立刻列出全部集、判断哪些已经在磁盘上。
   站点解析不了（断网 / 站点挂了 / 代理没开）时，这条路照样走得通。
2. **后台刷新**（`RefreshEpisodesSnapshotAsync`）：弹窗期间顺手抓一次页面，
   新更新的集**增量补进勾选框**（默认勾上）并提示"又发现 N 集"；抓不到就退化成
   "用的是本地数据"，已列出的集照旧能勾能下。弹窗里另有「刷新集列表」按钮
   —— 手动刷新走的是**同一段逻辑**（自动刷新没连上、或用户就是想再拉一次时用），
   刷新期间按钮变"刷新中…"并禁用，避免连点。

用户勾完把集号连同预检结果交回 `ResumeAsync(includeNewEpisodes: true, preview, onlyNumbers)`
—— 带着预检结果就不会再抓页面。新集才追加进任务分集清单，没勾的集不进任务、也不会被下。

**失败之后怎么办**（`SeriesTask.RoundUsedSnapshot`）：这一轮用的是本地快照、又有集没下成时，
收尾会**自动重新拉一次集元数据** —— 用旧快照续下失败，多半是站点改版让播放页地址失效了，
刷新之后用户点「重试失败集」就能用上新地址。刷新本身失败也不覆盖原来的失败原因。

### 快照里存什么、不存什么

| 存 | 不存 |
| --- | --- |
| 集号、标题、**播放页地址**、站点集标识（努努的 `ep_slug` 那种）、播放源 | m3u8 直链 —— 带时效签名、很快失效 |
| 站点请求头（Referer / Origin / UA）、站点类型、剧集 ID | 分片清单、密钥 —— 下载时现取 |

两个关键点：

- **不存直链也照样能下**：下载流程本来就逐集现解析（`SeriesDownloader` 每集下载前跑一次
  `ResolvePlaylistUrlAsync`），而适配器是**按每集 PageUrl 的 host** 挑的 —— 所以只要留下
  播放页地址与集标识就够了；
- **请求头必须存、且刷新时只能合并不许覆盖**：分片请求要带 Referer，而"重新解析刷新快照"
  那条路拿到的新 Headers 可能是空的（通用兜底解析器不填），直接覆盖会让续下时每个分片
  都被 403（见 `docs/pitfalls.md` 第 31 条）。

快照随任务落盘（老记录里没有该字段 → null，那类任务第一次续下会联网解析并补上）。

### 判定"下过没有"：以磁盘文件为准

| 判据 | 作用 |
| --- | --- |
| **磁盘文件**（权威，`EpisodeFileScanner`） | 按任务的产物目录 + 文件名模板**正向**算出这一集该叫什么，再看文件在不在；空文件不算下过 |
| 任务记录 | 只用来解释"为什么没有"：上次失败 / 上次取消 / 产物已丢失 |
| 下载历史（SQLite） | 文件被改名或搬走时说明"曾下载过，文件已不在" |

为什么不只信记录：任务列表会被「清理已完成」清掉、重装程序或换台机器就没了，
而视频还好好躺在文件夹里。为什么不拿正则去反推模板：`{title}` 会过一遍非法字符替换、
`{number:00}` 有补零差异 —— 正向算才能保证和下载时用的是同一套规则。

### 存储分工

| 数据 | 位置 | 说明 |
| --- | --- | --- |
| 设置 / 任务列表 / 下载历史 / 站点清单 | `<数据目录>\m3u8.db` | SQLite，实现在 `Core/Storage/` |
| 诊断日志 | `<数据目录>\logs\` | Core（每次启动一个文件） |

这几样数据**在同一个库里**，对应这些表：`settings`、`tasks` + `task_episodes`、
`task_snapshots` + `snapshot_episodes`、`downloads`、`sites`，另有 `meta` 存 schema 版本。

- `SqliteDatabase` —— 连接（`Pooling=false`、每次开连接设 `busy_timeout=3000`）、建表；
- `SqliteSettingsStore` —— **一行一列一项**（不是 key-value），读的时候缺列/为 NULL 一律退回
  代码里的默认值，所以加设置项不需要写迁移；
- `SqliteTaskStore` —— 任务 / 集 / 快照拆成四张表，`Save` 是"整表重写放一个事务"
  （中途失败整体回滚，比写 `.tmp` 再改名更稳），列表顺序靠 `sort_order`；
- `SqliteSiteStore` —— 站内搜索用的站点清单，`sort_order` 定下拉框顺序；**条数为 0 或库读不出来
  都退回内置清单**（下拉框空着等于这个功能没法用），地址不合法的行直接跳过；
- `SqliteDownloadHistory` —— 按 `(page_url, episode_number)` upsert（重下同一集只覆盖旧行），
  用户把任务**移除**时按 `page_url` 整部销掉（任务都没了，账留着只会在下次续下时凭空冒出
  "曾下载过"）——「清理已完成」不销账，那只是收拾列表，视频还在盘上，
  账要留着解释"文件已不在"。

早先这三样是**三个文件**（`settings.json` / `tasks.json` / `downloads.db`），只有历史那份用了
SQLite。合并的理由与代价写在 `AGENTS.md` 的「存储」一节；一句话版本是：
**存储实现只此一份，自检能直接测到真货**（以前实现挂在界面层，自检只碰得到替身，
SQL 得另起 `_diag` 项目兜），代价是三个入口各多带一个 `e_sqlite3.dll`（1.9 MB）。

两个实现上的注意点：**连接串要关掉连接池**（默认池化会让库文件被程序长期占用，
用户想删、想备份、想拿工具打开都会被"文件正在被使用"挡住）；**所有读写都要自己吞异常**，
存储坏了绝不该影响下载（设置退回默认值、任务读成空表、历史少一条账，程序照常跑）。
销账是磁盘 I/O 且由按钮触发，得扔到线程池上做，不能压在 UI 线程。

`<数据目录>` 由 `Core/AppPaths.cs` 统一决定，**优先程序目录下的 `data\`**：本程序是
"解压即用"的便携形态，整个文件夹拷到别的机器或 U 盘时，任务、设置、历史一起跟过去。
程序目录不可写时（`Program Files`、只读介质、被策略锁住）自动退回
`%APPDATA%\M3U8Downloader\`。

两个要点：**探测结果只算一次并缓存**（`Lazy`）—— 设置、任务、历史必须落在同一个目录，
各自探测一次一旦出现分歧，就会变成"设置读到了 A、历史写到 B"；**能不能用要真写一次才知道**
—— 只读介质上目录可能早就存在，只判断 `Directory.Exists` 是不够的。

**没有旧文件迁移**：合并进统一库时写过一版"三个文件 → 一个库"的迁移逻辑，后来删掉了
（个人项目，没有别的用户要照顾，也省得每次改 schema 都要照顾旧文件格式）。
所以库不存在就得到一个全新的空库；`data\` 里如果还留着 `settings.json` / `tasks.json` /
`downloads.db`，程序不会读它们。

`ffmpeg\` 不在这里：它有 300MB 量级、且属于可再下载的第三方二进制，沿用
`FfmpegLocator` 自己的"程序目录优先、`%LOCALAPPDATA%` 回退"逻辑（用 Local 而非 Roaming，
免得被域环境同步）。

## 广告/无效分片识别原理

`SegmentInspector` 用四重判据，命中任一即标记为可疑（可用 `--no-skip-ads` 关闭）：

1. **异目录聚类**：正常分片必然集中于同一目录。把分片按 URL 目录分组，占比低于 50% 的少数派目录即判为插播。
   注意分片直接放在域名根目录时（`https://host/seg0.ts`）必须归到根目录 `/`，
   否则每个分片都会被算成"各自的目录"，除第一片外全被判为异目录而整批跳过。
2. **重复分片**：同一分片地址在列表中重复出现 ≥3 次（通常在开头/中部/结尾各一次），是广告循环插入的特征。
3. **加密上下文突变**：整条流是 AES-128，个别分片却声明 `METHOD=NONE`。
4. **密钥可用性探测**：可疑分片引用的 `key.key` 实际请求一次，取不到即升级为「必然失败」。

判定结果会在界面日志与 CLI 输出中逐条列出原因，例如：

```
⚠ 检测到 12 个疑似插播广告/无效分片：
   · 发现 12 个分片来自异目录 /20260830/Kt5SzxVn/hls（主流目录 …/K2KZSZlA/1395kb/hls 含 1398 片）
   · 整条流为 1398 片加密，但有 12 片被声明为明文（METHOD=NONE）
   [319] 2Uog4J8A.ts (5s) 来自其他目录…；且同一分片重复出现 3 次；该片为明文段，与整条加密流不一致
   → 已启用自动跳过，这些分片不会导致任务失败。
```
