# M3U8 视频下载器（WinUI 3）

一个用 **C# / .NET 10 / WinUI 3** 编写的 HLS(m3u8) 视频下载器，参考 [Liubsyy/M3U8Quicker](https://github.com/Liubsyy/M3U8Quicker)（Tauri + Rust）的功能设计，并针对实际使用中遇到的**源站动态插播广告导致下载恒定失败**的问题做了专门处理。

---

## 为什么会有这个项目

用其他工具下载某短剧站的视频时，任务总是稳定报错「失败 12 片」，重试多次、换地址都没用。排查后发现根因：

- 该源站**每次请求 m3u8 都可能重新插入广告**：把 3 个位置各替换成同一组 4 个广告分片，合计 **12 片**；
- 广告分片指向另一个日期目录，而**那个目录的 `key.key` 已返回 404**；
- 广告片还被标记为 `#EXT-X-KEY:METHOD=NONE`（明文），与整条 AES-128 加密流不一致；
- 多数下载器**只判断 HTTP 状态码、不做内容校验**，于是这 12 片必然失败；而失败分片又会让整个任务判定为未完成。

本工具在**下载前**就把这类分片识别出来并剔除，因此同样的地址可以一次成功。
（插播是随机的：有时列表里没有广告，此时检测器也不会误报 —— 两种情况最终产物一致。）

## 功能

| 功能 | 说明 |
|---|---|
| **站点批量下载** | 粘贴视频网站播放页/详情页地址 → 自动识别站点 → 列出剧集 → 勾选后批量下载整部剧 |
| **下载任务队列** | 点「加入下载队列」立即入队并清空页面，可继续贴下一个地址；任务在「下载任务」里串行执行，实时显示进度 |
| **下载报告** | 下载结束后在视频目录生成 Markdown 报告（汇总 / 分集明细 / 产物校验 / 失败原因 / 运行日志）；单文件模式也会生成一份 |
| **广告/无效分片自动识别** | 基于「异目录聚类 + 重复分片 + 加密上下文突变 + 密钥可用性探测」四重判定，下载前剔除 |
| 多线程下载 | `Parallel.ForEachAsync` 并发调度，并发数可调（1–64） |
| 失败重试 | 单分片可重试，指数退避；任务级「重试失败集」 |
| AES 解密 | AES-128/192/256，**按密钥字节长度分派**（不信任 METHOD 字符串） |
| 断点续传 | 分片落盘，重新运行自动跳过已完成部分；**暂存目录带清单指纹**，列表变了就自动丢弃重下（见「暂存目录与校验」） |
| 内容校验 | 假 200/HTML 嗅探、Content-Length 校验、**合并产物全量逐包 TS 对齐校验** |
| 请求头支持 | 自定义 Referer / Origin / User-Agent（应对防盗链）；站点模式自动携带 |
| 清晰度选择 | 主清单自动选最高分辨率，也可列出全部 |
| **输出 MP4** | 合并后用 ffmpeg **流复制**转成 `.mp4`（`+faststart`）；未配置 FFmpeg 时退回保留 `.ts` |
| 保存路径 | 读取**系统真实下载目录**（支持被用户移动到 D 盘等情况），批量模式自动建剧名子目录 |
| **FFmpeg 集成** | 设置里可手动指定、或**应用内一键下载**（默认 LGPL 构建）；未安装也不影响下载本身 |
| **代理支持** | 仅用于「自动下载 FFmpeg」与**被墙站点的页面解析**（如努努影院），带连通性测试。**视频分片下载始终直连** |
| 设置与关于 | 设置落盘到 `%APPDATA%`；「关于」含版本、版权、许可证与第三方组件声明 |
| **托盘常驻** | 点关闭只是缩到右下角托盘，**下载在后台继续**；真正的退出入口是托盘右键菜单里的「退出」（[H.NotifyIcon](https://github.com/HavenDV/H.NotifyIcon)） |
| 图形界面 + 命令行 | WinUI 3 桌面界面（单文件 / 站点批量 / 下载任务 三个模式），另附 CLI 便于脚本调用 |

> 界面为单实例：重复双击图标不会再起第二个窗口抢带宽 —— 已有实例缩在托盘里的话会被叫回前台。
> 站点模式下并发总连接数 ≈ 同时下载集数 × 每集分片并发（默认 2×16=32）。

### 支持的站点

站点适配是**模块化**的：一个站点 = 一个 `ISiteAdapter` 实现类。
把类放进 `src/M3U8Downloader.Core/Sites/` 就会被自动登记，**不需要改任何注册代码**。

| 适配器 | 覆盖的站点形态 | 状态 |
|---|---|---|
| **努努影院** | nnyy.in 自研站点（`/{栏目}/{剧ID}.html`） | 已实测：解析出 9 个播放源 / 17 集；单集 951 分片下完并通过全部校验 |
| **苹果 CMS** | MacCMS v10 及其衍生模板，国内占比最高 | 已实测多个不同模板（含用原生形态 URL 的欧乐影院） |
| **通用解析（兜底）** | 页面里直接写着 m3u8 地址的站点 | 专用适配器都不认时自动出手 |

#### 苹果 CMS（MacCMS v10）

已实测通过多个不同模板的站点（播放页前缀各不相同）：

| 站点 | 播放页形态 | 实测 |
|---|---|---|
| 七猫短剧 | `/vodplay/30450-1-1.html` | 单源，源名 `360播放器` |
| 剧集搜 | `/v/7005-1-3.html` | **21 个播放源 / 336 集**，源名全部解析 |
| 欧乐影院 | `/index.php/vod/play/id/83912/sid/1/nid/1.html` | 原生形态 URL（**不是**伪静态），18 集；整站被墙，直连超时后自动走代理 |

第三种（`/index.php/vod/play/id/{id}/sid/{sid}/nid/{nid}.html`）是苹果 CMS **没开伪静态**时的原始地址。
只认伪静态那条规则的话，这类站点的详情页会被判成「不是苹果 CMS 站点」——
现在两种形态都会收集，连合成播放页地址时也按当前页面的形态来。

识别方式刻意**不写死 URL 前缀、不依赖 CSS 类名**：

- 从页面提取 `var player_aaaa={...}`（用**花括号配对法**解析 JSON 而非正则，因为 JSON 内含转义斜杠 `\/`）拿到本集 m3u8 直链；
- 剧中转场配置 `playerconfig.js` 的路径各站不同，因此**从页面 `<script src>` 自动发现**，而不是写死 `/static/js/playerconfig.js`；
- 剧集列表通过收集页内所有指向**同一剧集 ID** 的播放页链接、按集号排序得到，因此换模板也能用；同时按剧 ID 过滤掉侧边栏「猜你喜欢」里其他剧的链接；
- 多播放源默认只勾选当前页所在源，避免同一集被下载两遍。

> 官方 JSON API（`api.php/provide/vod/`）常被站长关闭（直接返回 `closed`），所以走 HTML 解析。
>
> 由于前缀不再写死，日期型路径（如 `/news/2026-09-13.html`）也可能"长得像"剧集页，
> 因此加了硬校验：苹果 CMS 播放页**必然带 `player_aaaa`**，没有就直接明确报错，不会产出垃圾结果。

#### 努努影院（nnyy.in）

这个站点不是苹果 CMS —— 页面和取流接口都是自研的：

| 环节 | 形态 |
|---|---|
| 详情页 | `/{栏目}/{剧ID}.html`，页内**没有**播放链接 |
| 集列表 | `<li class="play-btn" ep_slug="ep12">`，链接是 `javascript:;`，集号只在 `ep_slug` 里 |
| 取源接口 | `GET /_gp/{剧ID}/{ep_slug}` → `{"video_plays":[{"play_data":"…index.m3u8","src_site":"bfzy"}],"html_content":"<button>BF 第1集</button>…"}` |

**它是一个多源站点**，识别时会把每一集都问一遍，汇总成源列表交给用户选。
实测《交锋》解析出 9 个源（界面上「视频源」下拉里可切换）：

```
BF（bfzy）17 集 / MD（mdzy）17 集 / IK（ikzy）17 集 / LZ（lzzy）17 集 / UK（ukzy）17 集 /
FF（ffzy）16 集 / WJ（wjzy2）17 集 / SN（snzy）17 集 / YH（yhzy）16 集
```

三个实测出来的细节：

- **不同集的可用源并不相同**（第 1 集 9 个源、第 17 集只剩 1 个），所以不能只解析一次 ——
  识别阶段逐集调取源接口（17 集 ≈ 17 次小请求、约 34 KB，并发 5 条）；
- 源名沿用**站点自己在按钮上的叫法**（`BF`/`IK`…），括号里附上资源站代号（`bfzy`）；
  各源集数不一样（上面 FF 与 YH 就少一集），界面按源过滤，选哪个源就显示它有哪些集；
- 每集的直链在**识别阶段就确定了**，下载时不必再请求接口 —— 也就不会再消耗代理流量。

> 该站点挂在 Cloudflare 后面，国内直连会被重置（`curl: (35) Recv failure`），
> 因此它的适配器声明了 `NeedsProxy`：**只有取页面与取源接口走代理，分片下载仍直连**
> （实测 fengbao12、bfikuncdn 等 CDN 直连正常，42 秒下完 551 MB）。
> 只要「设置 → 代理」里填了地址就会自动生效，不用额外开关。

#### 通用解析（兜底）

没有专用适配器时，会直接从页面里找 m3u8 地址与「第N集」链接，能覆盖一批"页面里直接写着地址"的小站，
包括 JS 里的转义写法（`https:\/\/…`）。

**它认不了"地址由接口动态返回"的站点**（努努影院就是这一类），那种必须写专用适配器 ——
碰到这类页面它会明确报错，而不是返回一个空列表。

### 新增一个站点适配器

1. 在 `src/M3U8Downloader.Core/Sites/` 下新建一个类，实现 `ISiteAdapter`；
2. **不用注册**：`SiteResolver.CreateDefault()` 会反射扫描本程序集里所有实现，
   按 `Priority` 降序排列（认域名的专用适配器给正值，通用兜底固定 `-100`）；
3. 按需实现这几个成员：

| 成员 | 作用 | 默认 |
|---|---|---|
| `CanHandle(Uri)` | 只凭 URL 判断能不能处理，通常是「域名 + 路径形态」 | 必填 |
| `ParseAsync(html, pageUrl, ctx, ct)` | 解析剧集列表；能顺手解析出当前集直链更好 | 必填 |
| `ResolvePlaylistUrlAsync(episode, ctx, ct)` | 逐集补全 m3u8 直链（列表页不给直链的站点必须实现） | 必填 |
| `Priority` | 匹配优先级 | `0` |
| `NeedsProxy` | 页面是否需要代理（分片始终直连） | `false` |

4. 在自检的**阶段 J** 里补一段用本地页面 fixture 的断言（自检不依赖外网），
   照着 `NnyyAdapter` 的用例写就行。

### 分层与依赖方向

```
M3U8Downloader.Core        ← 零外部依赖（纯 BCL）：引擎、编排、持久化都在这里
      ▲        ▲        ▲
      │        │        │
    App       Cli    SelfTest
```

- **只允许单向依赖**：App / Cli / SelfTest 都只引用 Core，Core 从不反向引用它们
  （`Core.csproj` 里没有任何 `PackageReference`，也没有任何 `ProjectReference`）；
- Core 内部按职责分层：引擎（`HlsDownloader`）→ 单集流水线（`Downloads/EpisodePipeline`）→
  站点协调（`Sites/SeriesDownloader`）→ 任务队列（`Tasks/DownloadTaskManager`）；
- 界面只做两件事：把参数递进去、把日志与进度搬上来 —— **下载流程不写在 ViewModel 里**。

### 一条流水线，两种模式

「单文件下载」和「站点批量下载」曾经是两套并行实现：单文件那份写在
`MainViewModel.StartAsync()` 里，自己 new 引擎、自己跑解析与下载；于是站点模式有的
转 MP4、时长核对、产物体检、暂存目录指纹，它一样都没有。

现在两者都归结到 `Downloads/EpisodePipeline.RunAsync()`：

| 类型 | 负责 |
|---|---|
| `EpisodePipeline` | 一集的完整流程：解析清单 → 下载到暂存目录 → 转封装 MP4 → 容器探测 + 全量解码检查 → 清理暂存 |
| `SingleFileDownloadService` | 单文件模式入口：一个地址 → 一个产物 + 一份 `xxx-下载报告.md` |
| `SeriesDownloader` | 站点模式协调器：集间并发、进度聚合、分集报告与续传 |

流水线本身**不含任何站点概念**（没有剧集、没有集号），输入就是「一个播放列表地址 +
一个暂存目录 + 一个输出文件名」—— 所以图形界面、命令行、站点模式、单文件模式四处
走的是同一段代码，校验强度不会再出现落差（自检的阶段 I 守着这条）。

## 构建与运行

### 环境要求

- Windows 10 1809+ / Windows 11
- [.NET 10 SDK](https://dotnet.microsoft.com/download)（仅开发需要；运行发布版不需要）

### 构建

```powershell
cd M3U8Downloader
.\scripts\build.ps1
```

### 运行图形界面

```powershell
dotnet run --project src\M3U8Downloader.App -c Debug -p:Platform=x64 -r win-x64
```

界面右上角可切换两个模式：**单文件下载** 与 **站点批量下载**。
也可加 `--mode=batch` 直接以批量模式启动。

### 自检（无界面，不依赖外网）

```powershell
dotnet run --project tests\M3U8Downloader.SelfTest
```

会本地起一个极简 HLS 服务器（20 个分片 × 3 集）跑完整链路，分阶段校验：

| 阶段 | 校验内容 |
| --- | --- |
| A / A2 | 引擎上报频率、每集进度、总速度、分片级进度 |
| B | 任务队列：入队即可见分集清单、状态流转、绑定属性一律经 UI 线程封送 |
| C | 断点续传：存盘 → 关程序 → 恢复，已完成的集不重下、分片被复用 |
| D | 暂停 → 继续下载：必须停在「已暂停」（不是「失败」），续传能跑完，且停下后 6 秒不许再动 |
| E | 重试失败集：**任务数不变**、分集行数不变、已完成的集不被重下 |
| F / F2 | 续传只下原本选中的集：21 集里只勾第 12 集，续传后**计划里只能有 1 集**（多播放源时也一样） |

退出码 0 表示全部通过。阶段 E 是「点重试冒出重复集」那个 bug 的回归测试。

### 发布（自包含，免安装）

```powershell
.\scripts\publish.ps1              # 图形界面 + 命令行
.\scripts\publish.ps1 -Version 1.2.3   # 顺便把版本号写进 exe（CI 用 tag 作版本）
```

产物已内嵌 Windows App SDK 运行时与 .NET 运行时，**目标机器无需安装任何运行时**，
直接双击 `publish\app-win-x64\M3U8Downloader.exe` 即可。整体约 210 MB。
脚本末尾会自检 `hostpolicy.dll` / `coreclr.dll` / `Microsoft.WindowsAppRuntime.dll` 等是否齐全。

### 自动打包（GitHub Actions → Releases）

推一个 `v*` 的 tag 就会自动构建并发布到 Releases：

```bash
git tag v1.0.0
git push origin v1.0.0
```

`.github/workflows/release.yml` 里做的事：

1. 装 .NET SDK 10；
2. **先跑一遍自检**（本地 HLS 服务器，不依赖外网）—— 过不了就不打包；
3. 调 `scripts/publish.ps1 -Version <tag>`，与本地发布**同一条路径**，
   所以 CI 打出来的包和本地跑出来的不会有差别；
4. 压缩成两个 zip：`M3U8Downloader-<tag>-win-x64.zip`（界面）、`m3u8dl-<tag>-win-x64.zip`（命令行）；
5. 传到 Releases；同时留一份 artifact（30 天），Release 出问题时还能从 Actions 页面下载。

不想打 tag 也行：在 GitHub 的 **Actions → 打包发布 → Run workflow** 里手动触发，填个版本号即可。

> 包内**不含 FFmpeg** —— 它是独立的第三方组件，许可与体积都不适合打进包。
> 不做任何配置也能正常下载，只是产物保留 `.ts` 且跳过解码校验；
> 需要转 MP4 时在「设置 → FFmpeg」里一键下载即可。

## 命令行用法

### 单文件模式

```powershell
# 基本下载
m3u8dl "https://example.com/index.m3u8" -o D:\videos -n 第01集

# 带防盗链请求头
m3u8dl "https://example.com/index.m3u8" --referer "https://example.com/play/1-1.html" --origin "https://example.com"

# 只分析不下载（查看广告识别结果）
m3u8dl "https://example.com/index.m3u8" --dry-run

# 列出所有清晰度
m3u8dl "https://example.com/index.m3u8" --variants
```

### 站点批量模式

```powershell
# 识别站点并列出剧集（不下载）
m3u8dl --series "https://www.example.com/vodplay/30450-1-1.html" --list

# 下载指定集
m3u8dl --series "https://www.example.com/vodplay/30450-1-1.html" --episodes 1-8 -o D:\剧集

# 全部下载
m3u8dl --series "https://www.example.com/vodplay/30450-1-1.html" -o D:\剧集
```

### 选项

| 选项 | 说明 |
|---|---|
| `-o, --out <目录>` | 输出目录（默认 `用户\Downloads`） |
| `-n, --name <文件名>` | 输出文件名（不含扩展名） |
| `--referer <地址>` | 附加 Referer 请求头 |
| `--origin <地址>` | 附加 Origin 请求头 |
| `--ua <字符串>` | 自定义 User-Agent |
| `-c, --concurrency <n>` | 并发下载数，默认 16 |
| `--retries <n>` | 单分片重试次数，默认 3 |
| `--no-skip-ads` | **不**自动跳过疑似广告分片（默认跳过） |
| `--dry-run` | 只解析与分析，不下载 |
| `--variants` | 只列出所有清晰度 |
| `--log <文件>` | 把完整日志写入文件 |
| `--series <地址>` | 启用站点批量模式 |
| `--list` | 站点模式：只列出剧集不下载 |
| `--episodes <范围>` | 站点模式：选集，如 `1-8`、`1,3,5`、`2` |
| `--all-sources` | 站点模式：勾选全部播放源（默认只勾当前源） |
| `--ep-concurrency <n>` | 站点模式：同时下载集数，默认 2 |
| `--height <n>` | 优先选择指定高度的清晰度 |

### FFmpeg / 代理

| 选项 | 说明 |
|---|---|
| `--ffmpeg-status` | 查看 FFmpeg 检测结果（自定义路径 → 程序目录 → 用户目录 → 系统 PATH） |
| `--ffmpeg-download` | 应用内下载并安装 FFmpeg（默认 LGPL 构建，约 185 MB） |
| `--ffmpeg-url <url>` | 指定下载源（默认 BtbN 官方构建，国内可换镜像） |
| `--ffmpeg-path <exe>` | 手动指定 `ffmpeg.exe` 路径 |
| `--proxy <url>` | 代理地址（**仅用于 `--ffmpeg-download`**，视频下载始终直连） |
| `--proxy-test` | 测试代理连通性（与界面「测试」按钮**同一实现**） |

```powershell
# 走代理下载 FFmpeg，并验证装好没有
m3u8dl --ffmpeg-download --proxy http://127.0.0.1:7897
m3u8dl --ffmpeg-status

# 只测代理通不通
m3u8dl --proxy-test --proxy 127.0.0.1:7897
```

## FFmpeg 与代理

### FFmpeg 放在哪

安装位置遵循**"放在程序自己身边"**的原则，不往系统其它地方写东西：

| 优先级 | 位置 | 说明 |
|---|---|---|
| 1 | 设置里手动指定 | 复用你已有的 ffmpeg |
| 2 | **`<程序目录>\ffmpeg\`** | **默认安装位置**。整个文件夹拷到别的机器照样能用 |
| 3 | `%LOCALAPPDATA%\M3U8Downloader\ffmpeg\` | 仅当程序目录不可写时（如装在 `C:\Program Files\`）才用 |
| 4 | 系统 `PATH` | 找得到就用 |

> 严格门槛：`ffmpeg` 与 `ffprobe` **都**可用才算"已就绪"。只找到一半时界面会如实说明缺哪个。

### 为什么默认下载 LGPL 构建

本项目是 Apache-2.0，且只把 FFmpeg 当**独立进程**调用（转封装用 `-c copy` 流复制，不重新编码），
用不到 libx264 等 GPL-only 组件。选 LGPL 构建可以让分发链路上不引入额外的 GPL 义务，体积也更小
（LGPL ≈ 133 MB，GPL ≈ 164 MB）。需要 GPL 特性时可在设置里改下载源，详见
[THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md)。

### 代理（只用于获取 FFmpeg 与被墙站点的页面解析）

**代理默认关闭；填了地址之后，也只有真正需要它的环节才会走。**

| 环节 | 是否走代理 | 说明 |
|---|---|---|
| 站点页面（列剧集、解析直链） | ⚠️ 直连优先，不通才换 | 绝大多数站点直连即可；被墙的（努努影院连接被重置、欧乐影院直连超时）自动回退 |
| 视频分片下载 | ⚠️ 直连优先，**按主机记忆** | 通畅时零代理开销；某台主机直连不通、或被 403 拒绝，就记住它，之后该主机一律走代理 |
| 密钥 / 直链可用性探测 | 同上（走同一个请求入口） | 不这样的话，网络不通会被误判成「密钥不可用 → 这一片是广告」 |
| **下载 FFmpeg** | ✅ 需要时走代理 | 唯一要访问 GitHub 的环节，国内直连通常不通 |

几个刻意的设计：

- **默认全部直连**，只有两种情况才改用代理：直连失败（超时 / 连接被重置），
  或者直连**连上了却被 403/451 拒绝** —— 墙外 CDN 常用「按 IP 直接 403」这一招，
  实测欧乐影院的 `europe.olemovienews.com` 就是：国内直连 403、代理 200；
- **回退按主机记忆**：记住之后，同一主机的后续请求直接走代理。
  否则每个分片都要先白等一次连接超时，一千个分片就是几个小时的冤枉时间；
- 404/410 这类「资源真没了」**不会**触发代理（换了也没用）；
- 连接超时压到 8 秒，用户不用干等；
- 只要在「设置 → 代理」里填了地址就生效，**不需要其它开关**
  （刻意不看「下载 FFmpeg 时使用代理」那个勾：填了地址就说明这台机器上有代理可用）。

> 日志里会写明这一趟到底走没走代理：
> 「直连 olevod.com 不通，已自动改用代理」/「xxx 直连不通，已改用代理下载」。
>
> 声明 `NeedsProxy` 的站点若没填代理地址，解析时会直接告诉你
> 「该站点的页面需要通过代理访问」并附上直连的失败原因，
> 而不是丢一句看不懂的连接错误。

## 下载任务与报告

### 任务队列

在「站点批量下载」里选好剧集后点 **「加入下载队列」**：

1. 任务**立即入队**（毫秒级返回），当前页面随即清空，可以直接贴下一个地址；
2. 界面自动切到 **「下载任务」** 面板，能看到每个任务的进度条、已完成集数、速度、状态与消息；
3. 队列**串行执行**：一次只跑一部剧。每部剧内部已有「集并发 × 分片并发」，
   再叠加多任务并发会把连接数打爆，也让进度难以理解；
4. 每个任务可单独「暂停 / 继续下载 / 取消 / 重试失败集 / 下载报告 / 打开目录 / 移除」。

面板上会实时显示：任务合计速度（`↓`）与上传速度（`↑`，本程序不上传任何数据，恒为 0，
因此**只在真的有任务在跑时才显示**）、以及 `共 N 个任务 · 下载中 x · 已暂停 y · 排队 z …` 的汇总。

每个任务就是一个**展开栏**：**标题行**是任务速览 ——
`状态 · 剧名 · 站点与目录 · 已下载集数/总数 · 整体进度条 · 速度或说明`
（下载中显示 `↓ 8.42 MB/s · 00:06:12 · 312.0 MB`，停下则显示为什么停的），
展开后才是分集清单与操作按钮。所以收起分集清单也能一眼看清是哪部剧、下到哪了。

分集清单**左右各留 20px 内缩**（之前是紧贴卡片左边框，连缝隙都没有），
集号文字与标题行的内容大致对齐。每一集显示
**进度条 + 百分比 + `183/941 片` + 状态**。
一集动辄上千个分片，百分比会长时间停在同一个数字上，**分片计数才是"确实在动"的证据**；
正在下载的那一集还会写成 `正在下载 第12集 · 62% · 183/941 片`，随时能看出在下什么。

### 诊断日志（排查"停不下来"这类问题用）

「下载任务」面板右上角的 **「日志」** 按钮会打开 `%APPDATA%\M3U8Downloader\logs\`。
每次启动写一个新文件，只记**状态变化**（不记分片、不记内容）：

```
15:34:31.204  [a1b2c3d4 交锋] 用户点了暂停（下载中）
15:34:31.980  [a1b2c3d4 交锋] 本轮结束：已暂停，0.8s，成功 0 / 失败 0 / 取消 1，完成集 (空)，失败集 (空)
15:34:52.117  [a1b2c3d4 交锋] 用户点了继续下载
15:34:53.006  [a1b2c3d4 交锋] 开始下载：1 集（12），并发 2 集 × 16 分片
15:34:53.011  [a1b2c3d4 交锋] 第12集 Pending → Downloading（0%，总 0.0%）
15:36:02.887  [a1b2c3d4 交锋] 第12集 Downloading → Completed（100%，总 100.0%）
15:36:03.402  [a1b2c3d4 交锋] 本轮结束：已完成，70.4s，成功 1 / 失败 0 / 取消 0，完成集 12，失败集 (空)
```

「某一轮到底领到了哪几集」（`开始下载：N 集（…）`）是关键 ——
出现"暂停了还在下""继续下载停不下来"时，看这几行就能判断是任务在反复重下，
还是同时有别的任务在跑。文件超过 4 MB 自动停止写入。

### 暂停与继续

- **暂停**：停下这一轮下载，**已经下好的分片留在暂存目录里**，不会白下；
  任务落到「已暂停」，界面上给的是「继续下载」而不是「重试失败集」；
- **继续下载**：重新解析站点（m3u8 直链有效期很短），只补没下完的集，
  暂存目录里的分片按清单指纹校验后接着用；
- 暂停那一刻**真的失败**的分集（比如源站刚好返回 404）会如实保留「失败」字样 ——
  继续下载时同样会被补下，不会因为「已暂停」三个字把问题藏起来。

### 重试失败集

「重试失败集」是在**原任务上就地重试**：失败的那几集回到「等待中」再下一次，
已完成的集不会重下（作为上一轮的成果写进报告），**任务列表里始终只有这一条任务**。

> 早期的实现是"照抄剧集列表再建一个新任务"，同一个任务因此在列表里出现两份
> （新的那份把失败的集从头再列一遍，老的那份还挂着「已取消」），点几次就冒出几批重复的集。
> 现在这条路径由自检的阶段 E 守着（见下文「自检」）。

### 关掉程序也不丢进度（断点续传）

任务列表保存在 `%APPDATA%\M3U8Downloader\tasks.json`，记着每个任务每一集的状态、
百分比、产物路径与下载参数。因此：

- **重新打开程序，任务还在**，并自动切到「下载任务」面板给出提示；
- 没下完的任务会**自动接着下**：已下好的集不会重下，正在下的那一集从上次的分片接着下；
- 记录说下好了、产物文件却已被删掉的集，会被识别出来**重新下载**；
- 因「部分完成 / 失败 / 关窗打断」而停下的任务，面板上会出现 **「继续下载」**：
  重新解析站点后只补下缺的那些集，并把上次已完成的集一并写进新报告；
- 站点解析失败（断网、站点改版）时停在原地并提示原因，点「继续下载」即可重试。

关窗那一刻会立刻写盘一次，所以正在下载的进度也不会丢。

### 下载报告

整部剧结束后，会在视频目录里生成 `剧名-下载报告.md`，包含：

- 站点、页面地址、使用的播放源、输出目录、耗时、产物格式；
- **汇总**：成功/失败/取消集数、总大小、总时长、自动跳过的广告分片数；
- **产物校验**：逐项列出校验覆盖与结论（见下表）；
- **分集明细**：每集的时长、大小、分片统计、**编码 / 分辨率与帧率 / 音频声道**、时长核对、解码检查、产物文件名；
- 失败与取消的集，附上**保留下来的暂存目录路径**；
- 完整运行日志。

### 用 ffmpeg 做哪些校验（以及都写进报告）

FFmpeg / FFprobe 在整条链路里承担四件事，**每一项的结论都会进报告**：

| 用途 | 命令 | 报告里体现为 |
| --- | --- | --- |
| 转封装 MP4 | `ffmpeg -c copy -movflags +faststart` | 产物格式、运行日志 |
| 容器探测 | `ffprobe -show_entries format,stream` | 明细表的 `编码` / `分辨率 / 帧率` / `音频` 三列 + 日志里的码率 |
| 时长核对 | `ffprobe` 或内置探测 | 明细表的 `时长核对` 列（通过 / 不通过 / 未完成） |
| **全量解码检查** | `ffmpeg -v warning -i X -f null -` | 明细表的 `解码检查` 列 + 「产物校验」表里的一行 + 告警汇总 |

**全量解码检查**是唯一能发现"容器、时长、包对齐全对，但内容里混了源站坏包"的手段。
实测某站 16 集里有 3 集报 `Packet corrupt` / 音频时间戳非单调 —— 那是源站数据问题，
不是拼接错位，只有整条解一遍才看得出来。

它的代价是**要把产物整条读一遍**（实测 400 MB 约 35 秒）。嫌慢可以在
「设置 → 下载默认值」里关掉（`FullDecodeCheck`），关掉后报告里那一列会显示为未执行，
其余校验不受影响。

### 报告的「产物校验」表长这样

```markdown
## 产物校验

| 校验项 | 覆盖 | 结果 |
|---|---|---|
| 分片落盘与合并字节核对 | 16 集 | ✔ 全部通过（不多不少） |
| 时长核对（清单声明 vs 产物实际） | 16/16 集 | ✔ 全部通过 |
| 容器探测（格式/编码/分辨率/帧率） | 16/16 集 | ✔ 已记录，见明细 |
| 全量解码检查（ffmpeg -f null -） | 16/16 集 | ⚠ 3 集有解码告警 |
```

有解码告警时，报告里会额外用引用块列出**是哪几集、报了什么**，
并说明"通常是源站数据问题，不是拼接错位"。

## 托盘与后台运行

**关掉窗口 ≠ 关掉程序**：下载任务要在后台跑完，所以窗口关闭只是「缩起来」。

| 操作 | 行为 |
| --- | --- |
| 点窗口右上角「✕」（或 Alt+F4） | 窗口隐藏到右下角托盘，**下载继续跑**；第一次还会弹个气泡提示 |
| 单击托盘图标 / 右键菜单「打开主界面」 | 窗口回来并置前（不移除任务，不打断下载） |
| 右键菜单「退出」 | **唯一真正退出的入口**：先落盘任务进度 → 摘掉托盘图标 → 关窗结束进程 |
| 开始菜单/桌面再点一次程序 | 不新开窗口；已缩在托盘的实例会被叫到前台 |

托盘图标用的是 [H.NotifyIcon](https://github.com/HavenDV/H.NotifyIcon)（MIT）的 WinUI 版 `TaskbarIcon`：
图标、气泡通知、右键菜单都由它提供。声明集中在 `src/M3U8Downloader.App/TrayIconResources.xaml`
（`XamlUICommand` + `ContextFlyout`，写法与官方 WinUI 示例一致），装配在 `App.xaml.cs` 的
`InitializeTrayIcon()` 里。

几个刻意的选择：

- **关闭拦截用 `AppWindow.Closing` + `args.Cancel = true`，而不是 `Window.Closed`**：
  `Closed` 触发时窗口已经在关，而 `MainWindow` 的 `Closed` 处理器要做「落盘 + 释放任务管理器」，
  一旦这次关闭被取消，正在跑的后台下载会被连带释放掉。
- **不开效率模式**：`ForceCreate(enablesEfficiencyMode: false)`。库默认会启用 Windows 11 的
  效率模式，但窗口藏起来之后 AES 解密、TS 合并、ffmpeg 校验还在跑，降频会实打实拖慢这几步。
- **托盘起不来就退回「点关闭即退出」**：`ForceCreate` 抛异常时会把 `MinimizeToTrayOnClose`
  置回 false —— 绝不能出现「窗口藏起来了，却没有图标能把它叫回来」。
- 「设置 → 下载默认值」里可以关掉「点关闭按钮时最小化到托盘」（`MinimizeToTrayOnClose`），
  关掉后恢复传统行为：点关闭就是退出。

> 关机/注销由系统接管，不保证走上面的退出流程；此刻的进度依赖断点续传兜底 ——
> 已下完的分片带清单指纹留在暂存目录里，下次接着下。

## 产物校验（下载完到底查了什么）

下载完成时，"成功"不是靠一句 `OK` 得出的，而是逐层查出来的。**没通过校验的一律不算成功**：

| 层级 | 查什么 | 不过会怎样 |
| --- | --- | --- |
| 清单/密钥 | 响应不是 HTML/JSON 错误页（挡"假 200"） | 报错并停止，不做无意义的重试 |
| 每个分片 | HTTP 2xx + `Content-Length` 与实际字节数一致（挡截断响应） | 该片重试，仍失败即计失败 |
| 解密结果 | TS 同步字节 `0x47`（严格版查 20 个包起点，宽松版用来在多种填充策略里挑正确解） | 换备用密钥再试，仍不行才算失败 |
| 分片落盘 | 应该存在的分片**是否真在磁盘上**、大小是否与记录相符 | 记为"落盘核对异常"并写进报告 |
| 合并结果 | 字节数与"应拼入的分片之和"完全相等（不多不少） | 判为不完整，**不清理暂存目录** |
| TS 产物 | **全量逐包** 188 字节对齐（400MB 约 1 秒） | 判为"拼接错位"，保留现场 |
| 产物时长 | 用内置探测（TS 读 PCR / MP4 读 mvhd）读真实时长，与清单声明值比对（容差 5% 且 3s） | 报"可能缺片"，建议核对原播放列表 |
| **产物解码** | `ffmpeg -f null -` 整条解一遍，统计坏包/时间戳告警 | 报告里标"有解码告警"，并列出是哪几集、报了什么 |

"合并字节数核对"和"产物时长核对"是后补的两道闸门 —— 它们堵的正是那种最阴的失败：
**分片少了、产物静默缺一段，但 ffmpeg 退出码是 0、文件大小看着也正常**。

时长核对优先用**内置探测**，不依赖外部工具：TS 累加 PCR 相邻差值（天然容忍计数回绕），
MP4 读 `moov → mvhd` 的 duration/timescale。两边都读不出来时会明确报"时长核对未完成"，
**不会**假装通过。

### 仍然查不到的（如实说明）

- **解码正确性**：只查 TS 包同步字节，不查 H.264/AAC 内容是否有损坏。源站本身返回坏数据时，
  产物能通过格式校验，但播放器可能出现花屏/丢帧（实测 16 集里有 3 集报 `Packet corrupt`，
  是源站数据问题，不是拼接问题）。
- **音视频是否同步**：不做 A/V 同步检查。
- **时长核对依赖流里有时间戳**：既没有 PCR 时间戳、也没有 ffmpeg 的极端情况下读不出时长，
  只能报"未完成"。

自检阶段 G 会验证"内置时长探测"本身：构造一条 PCR 跨度为 42 秒的 TS，要求读回 42.00s。

## 暂存目录与校验（一集一个目录，全过才清理）

每一集下载时都使用**自己专属的暂存目录**，就放在**下载目录里面**：

```
下载目录\交锋\
├── 交锋.01.mp4                     # 最终产物（常用格式）
├── 交锋-下载报告.md
└── .m3u8tmp-001-a1b2c3d4\          # 本集的暂存目录（成功后自动删除）
    ├── manifest.json               # 清单：播放列表、分片数、时长、跳过项、指纹、产物路径
    ├── seg_000000.ts               # 分片
    └── merged.ts                   # 合并后的中间文件
```

- **放在下载目录里**（而不是系统临时目录）：便于发现与清理，出问题时也容易找到；
- **名字带集号与随机串**（`.m3u8tmp-<集号>-<8位随机>`）：同一集并发/重试时不会互相踩；
- 流程：**下载 → 合并 → 转 MP4 → 全量校验 → 全部通过才删除暂存目录**；
- **中间任何一步出错都不删**：失败时暂存目录连同分片一并保留，
  报告里会写明路径，便于排查或下次重试；
- **再次下载同一集时直接复用这个目录**：里面已经下好的分片跳过不重下，剩下的接着下。
  复用是安全的 —— 分片还能不能用由下面说的清单指纹判断。

### 为什么清单里要存"指纹"

源站可能**每次请求都重新生成播放列表**（典型做法是随机插播广告），于是
「分片序号 ↔ 内容」的对应关系在不同次请求之间会变。若直接复用上一次的残留分片，
就会拼出一个**错位的文件** —— 而且大小往往看着很正常，极难发现。

因此续传前先比对指纹：

| 情况 | 处理 |
|---|---|
| 指纹一致 | 复用已有分片，正常断点续传 |
| 指纹不一致（列表被重新生成） | **丢弃旧分片重新下载**，并在日志里说明原因 |
| 有分片但没有清单（旧版本残留） | 同样丢弃 —— 无法确认对应关系 |
| 目录里有非本程序生成的文件 | 只清理自己的分片，**保留目录**，绝不误删用户文件 |

### 校验强度

合并产物做的是**全量逐包检查**：每个 188 字节包的同步字节都必须是 `0x47`，
且文件长度必须是 188 的整数倍。

早期实现只在"文件头、正中间、尾部"各抽查 3 个字节 —— 中间任何位置错位都发现不了，
那种校验基本没有意义。全量扫描 400MB 约 1 秒，代价完全可以接受。

## 广告/无效分片识别原理

`SegmentInspector` 用四重判据，命中任一即标记为可疑（可用 `--no-skip-ads` 关闭）：

1. **异目录聚类**：正常分片必然集中于同一目录。把分片按 URL 目录分组，占比低于 50% 的少数派目录即判为插播。
   注意分片直接放在域名根目录时（`https://host/seg0.ts`）必须归到根目录 `/`，
   否则每个分片都会被算成"各自的目录"，除第一片外全被判为异目录而整批跳过。
2. **重复分片**：同一分片地址在列表中重复出现 ≥3 次（通常在开头/中部/结尾各一次），是广告循环插入的特征。
3. **加密上下文突变**：整条流是 AES-128，个别分片却声明 `METHOD=NONE`。
4. **密钥可用性探测**：可疑分片引用的 `key.key` 实际请求一次，取不到即升级为「必然失败」。

判定结果会在界面日志与 CLI 输出中逐条列出原因，例如：

```
⚠ 检测到 12 个疑似插播广告/无效分片：
   · 发现 12 个分片来自异目录 /20260830/Kt5SzxVn/hls（主流目录 …/K2KZSZlA/1395kb/hls 含 1398 片）
   · 整条流为 1398 片加密，但有 12 片被声明为明文（METHOD=NONE）
   [319] 2Uog4J8A.ts (5s) 来自其他目录…；且同一分片重复出现 3 次；该片为明文段，与整条加密流不一致
   → 已启用自动跳过，这些分片不会导致任务失败。
```

## 实现中踩过的坑（已修复，供参考）

1. **AES 填充策略**：HLS 的 AES-128 分片通常带 **PKCS7 填充**。若错误地用「无填充 + 截断到 16 字节整数倍」处理，每片会丢掉 4–15 字节，拼接后 **188 字节 TS 包整体错位** —— 文件大小看着正常、实测包同步率只有 2%，根本无法播放。本工具按 PKCS7 → 无填充+188 对齐 的顺序尝试并校验结果。

2. **密钥按长度分派**：部分源站把 AES-192/256 错标为 `AES-128`，所以要按**密钥实际字节长度**（16/24/32）决定算法强度，而不是照 METHOD 字符串走。

3. **IV 推导**：`EXT-X-KEY` 未显式给出 IV 时，按规范用**媒体序号**（`MEDIA-SEQUENCE + 索引`，16 字节大端）推导，而不是列表索引。

4. **重定向后 URL 作基准**：解析相对路径必须用 `HttpClient` 重定向后的**最终地址**，否则经 CDN 跳转会解析到错误域名。

5. **假 200 与截断响应**：不少源站用 `200 + HTML 错误页` 冒充成功，或提前截断响应。需要嗅探 HTML、校验 Content-Length。

6. **路径中的双斜杠不能归一化**：某些源的主清单是 `/20260906/xx//1395kb/hls/index.m3u8`，把 `//` 折叠成 `/` 会直接 404。

7. **WinUI 3 部署**：非打包（unpackaged）应用若不自包含，会因缺少 DDLM 包而弹「Windows App Runtime 组件缺失」。设 `WindowsAppSDKSelfContained=true` + `SelfContained=true` 可彻底免除依赖。

8. **勾选状态不会回写**：WinUI 的 `CheckBox` 双向绑定要求属性实现 `INotifyPropertyChanged`。Core 模型保持朴素，界面侧用 `EpisodeItemViewModel` 薄包装。

9. **并发是嵌套的**：站点模式下总连接数 ≈ 集数并发 × 每集分片并发（默认 2×16=32），不要盲目调大。

10. **别硬编码下载目录**：`%USERPROFILE%\Downloads` 与**系统真实下载目录**可能不是同一个位置（用户可以把「下载」文件夹移到别的盘）。而且 `%USERPROFILE%\Downloads` 往往**仍然存在**，于是程序会**静默存到错误的地方**——不报错，但你在下载文件夹里找不到文件。正确做法是向 Shell 查询 `FOLDERID_Downloads`（见 `Core/KnownFolders.cs`）。

11. **WinUI 下读命令行**：`Environment.GetCommandLineArgs()` 在 WinUI 的启动路径里不保证可靠（实测会返回空，导致启动参数失效），应改用 Win32 `GetCommandLineW`。

12. **PowerShell 脚本编码**：Windows PowerShell 5.1 读取**无 BOM 的 UTF-8** 脚本时会按系统 ANSI 代码页（中文系统为 GBK）解码。含中文的脚本若不加 BOM，中文字符的尾字节会把后面的引号吞掉 → 语法错误。含中文的 `.ps1` 请存为 **UTF-8 with BOM**，或只用 ASCII。

13. **根目录分片被整批当广告跳过**：目录聚类用「路径里最后一个 `/` 之前的部分」当目录键，而 `/seg0.ts` 的 `LastIndexOf('/')` 是 0，直接切片会得到 `/seg0.ts` 本身 —— 每个分片都成了独立目录，于是除第一片外全被标记为「异目录插播广告」并跳过。结果是一集只下了 1 片却报"成功"，产物小得离谱。目录键必须把这种情况归到 `/`。同时增加了保护：跳过比例超过 30% 时明确告警。

14. **绑定属性必须在 UI 线程改**：`SeriesTask` 的属性直接绑到 `ListView`，而下载回调来自后台线程。WinUI 里从后台线程改绑定属性**不报错但界面不刷新**，现象就是任务永远停在「下载中」，进度条一动不动。`DownloadTaskManager` 因此统一通过 `uiInvoker`（`DispatcherQueue.TryEnqueue`）封送所有状态写入；后台 worker 也不再去遍历绑定用的 `ObservableCollection`，改用内部待执行队列。

15. **暂存目录每次换名字 = 断点续传形同虚设**：暂存目录原本每次下载都新建一个带随机后缀的名字，于是上次下到一半的分片**虽然保留着，却永远不会再被用到** —— 关掉程序重开后整集重下。现在同一集已有暂存目录就直接复用，由引擎的清单指纹决定哪些分片还能用。

16. **异步封送下"先写后跑"的顺序**：恢复任务时要先把 `Series` / `Options` 写进任务对象再入队。`DispatcherQueue.TryEnqueue` 是**异步**的，如果写完就立刻入队，worker 可能先拿到任务、读到的却是 `null`，任务会直接判失败。这类"设置状态 → 交给后台消费"的地方必须等封送真正执行完（自检里就是靠这一点抓出来的）。

17. **「重试失败集」不该新建任务**：原先的实现是 `Enqueue(SelectOnly(task.Series, failedNumbers), …)`，也就是照抄剧集列表再建一个**新任务**。于是同一个任务在列表里出现两份：新任务把失败的 21 集从头再列一遍，老任务还挂着「已取消」，点一次「重试失败集」就多出一批重复的集。正确做法是**在原任务上就地重试** —— 失败的那几集回到「等待中」，已完成的集作为上一轮的成果带进报告但不重下。

18. **取消标记是一次性的**：`CancellationTokenSource` 取消过就废了。暂停/取消之后如果直接再入队，新的一轮会**一启动就被判取消**（界面上就是一句莫名的 "The operation was canceled."）。所以每次真正开始下载前都要换一个新的 `Cts`；「继续下载」里更要在**重新解析站点之前**就换 —— 那次解析用的就是这个 token。

19. **排队等并发名额的集会把整批下载拖垮**：暂停/取消时，还在 `SemaphoreSlim.WaitAsync(ct)` 上排队的那些集会让它抛 `OperationCanceledException`。这个异常冒到 `DownloadAsync` 外面，整批下载就以异常收场：任务被判成「失败」，连下载报告都拿不到。必须在入口处接住它，按「还没开始下载」处理（暂存目录里的分片照旧保留）。注意这段 catch **不能**并进下面那个带 `finally { gate.Release(); }` 的 try —— 名额根本没拿到，Release 会把信号量计数搞坏。

20. **暂停不是取消**：暂停后如果只把状态对成 `Canceled`，用户看到的是「已取消」，还会同时冒出「继续下载」和「重试失败集」两个语义矛盾的按钮。暂停要有独立状态（`Paused`），并且只把**被暂停打断的**那些集改写成「已暂停」——暂停那一刻**真的**失败的分集（比如源站刚好 404）要如实保留，否则等于把真实问题藏起来。

21. **进度上报必须限流，但收尾那一次不能省**：引擎每几十毫秒上报一次，每次都 `DispatcherQueue.TryEnqueue` 一个闭包的话，UI 线程会被写入淹掉，表现就是"进度条不动、消息一句话不变"。限流到 100ms 一次之后就顺了。**但轮次收尾那次必须强制放行**——它带着各集的最终状态，被限流吃掉的话分集行会永远停在「下载中」（自检阶段 D 抓到的就是这个）。

22. **"百分比不动"不等于"没在下载"**：一集可能有近千个分片，百分比在几十秒里看起来是同一个数。界面必须显示分片计数（`183/941 片`），并且让每一轮明确写出"这一轮领到了哪几集"——否则用户没法判断程序在下什么。

23. **多源站点按集号选集会重复下载**：`SiteSeries.AllEpisodes` 是"所有源 × 所有集"的笛卡尔积，同一个集号在不同源上都有一份。用 `SelectOnly(series, {12})` 这种"只按集号"的写法，会**一次选中好几个同号集**，引擎于是把第 12 集下了两遍（诊断日志里是 `计划 2 集（12,12）`）。选集必须按 **(源 id, 集号)** 成对匹配。
